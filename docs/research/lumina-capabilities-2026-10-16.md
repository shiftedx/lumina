# Lumina playback and integration capability audit — 2026-10-16

This is a source audit of Lumina's current production code, ADRs, and focused tests. It is intended to pair with a separate SoulSync assessment: it establishes what Lumina already has, so a competitive roadmap does not propose rebuilding it.

## Confidence labels

* **Implemented and tested** means production code plus a focused unit, API, or browser test were found. This is not a claim that it was tested against every physical device or a live arr installation.
* **Implemented, integration unverified** means the code has a defined external boundary, but this audit found fakes/mocks rather than a real-device or real-service test.
* **Partial** means the underlying capability exists with an explicit limitation.
* **Absent in the audited surface** means a repository-wide search of production `backend/app`, `frontend/src`, ADRs, and operator documentation found no implementation. It is not proof that a client app using Lumina's Jellyfin API cannot provide that feature itself.

## Explicit limitations and missing playback surface

These are the likely competitive gaps, separated from capabilities that are merely delivered through a different client.

| Priority | Gap | Evidence | Recommended product direction |
| --- | --- | --- |
| P0 | **No server-owned device handoff/session continuity.** Progress follows a member, but a playing browser video/music session cannot be moved to a selected TV/speaker with queue, position, state, and controls preserved. | Music casting stops browser playback and constructs a Sonos-only queue (`frontend/src/features/music/MusicPlayer.tsx:112-133`); browser music queue persistence is local-only (`frontend/src/features/music/musicSession.ts:84-115`). Jellyfin clients have independent sessions. | Define a small `PlaybackSession` domain above transports: member, queue/playlist version, active item/version, position, state, output target, and capabilities. Start with browser ↔ Sonos music and browser ↔ Jellyfin-device handoff; do not make the Jellyfin API itself the session authority. |
| P0 | **Video has no first-party casting surface.** No production implementation was found for Chromecast/Google Cast, AirPlay, DLNA/UPnP video, or a device picker. | Repository-wide production search finds only the Sonos music cast implementation (`backend/app/services/music_sonos.py`, `backend/app/routers/music.py`). Jellyfin client playback is a valuable indirect route but does not give Lumina a unified device-control UX. | Add an output-provider abstraction only after the handoff model exists. Prefer a narrow first adapter selected by household demand (Google Cast or AirPlay), and retain Jellyfin as an external-player target rather than reimplementing every device protocol. |
| P0 | **Local converted HLS has no ABR ladder; remote upstream streams already do.** Local video offers original/manual quality and one converted rendition, while remote DASH/HLS supports automatic adaptation and explicit quality pins. | The local `master_playlist` is explicitly one-rendition (`backend/app/services/local_playback_sessions.py:335-339`) and its quality changes restart a session (ADR 0012). Remote HLS exposes its upstream ladder to hls.js (`frontend/src/remotePlayer.tsx:112-117`, `358-379`); remote DASH enables measured-throughput ABR (`frontend/src/remotePlayer.tsx:421-446`), qualified in `docs/performance/remote-streaming-2026-10-11.md:3-24`. | Keep remote ABR intact. Build a local multi-rendition ladder only if remote/mobile viewing data shows recurrent buffering; first improve the manual local-quality recommendation from observed stalls, then add a bounded 2–3-rung ladder sharing a session budget. |
| P1 | **Music has gapless playback but no crossfade.** This is a feature distinction worth preserving: crossfade must not be mistaken for gapless. | The engine schedules exactly at the previous buffer boundary (`frontend/src/features/music/musicEngine.ts:748-759`); there are no gain-ramp/crossfade controls in the music engine/session/UI. | Add an optional 0–12 s equal-power crossfade in the Web Audio path, disabled by default for sequential album playback. Keep large-file streaming clearly non-gapless until a segment-aware audio solution exists. |
| P1 | **Offline is music/browser-only.** There is no offline video/TV, server-synced offline catalog, or device-storage manager. | ADR 0023 scopes offline to owner-scoped browser storage and the static listening shell; `frontend/src/features/music/musicOffline.ts:13-18`. | Treat music offline as complete enough for now. If adding video downloads, first define member visibility/revocation behavior, storage quotas, and an explicit offline-catalog lifecycle; do not reuse the generic service-worker cache for authenticated media. |
| P1 | **Subtitle preferences are partial.** Lumina persists a member's caption presentation (size/background) and applies it to Lumina videos, but it has no member-persisted content-selection defaults for preferred subtitle/audio language, subtitles on/off, or forced/SDH policy; Jellyfin clients have separate controls. | Caption presentation is stored in `ui_prefs.captions` (`frontend/src/features/watch/captionPrefs.ts:1-27`), synced by the member settings merge (`backend/app/services/user_settings.py:93-105`), and declared to apply to every Lumina video (`frontend/src/features/settings/sections/you.tsx:182-187`). Local track choice remains a per-session request (`backend/app/routers/local_playback.py:170-173`). | Add content-selection defaults (language, enabled state, forced/SDH policy, audio language) to the playback-preference model and map them into browser and Jellyfin decision paths. Treat translation/ASR outputs as reviewable generated artifacts under ADR 0013, not direct model truth. |
| P1 | **Playback quality behavior is mostly reactive.** There is a lower-quality offer after repeated browser stalls, but no per-network/device quality policy or measured ABR. | The local player offers one lower rung after three waits in 60 seconds (`frontend/src/localPlayer.tsx:313-335`). | Use a small stored per-device/network preference and runtime metrics to preselect a safe starting rung, with a user override. |
| P2 | **No broad music output ecosystem.** Sonos is strong and security-conscious, but there is no first-party Chromecast, AirPlay, DLNA renderer, Bluetooth/native companion, or multi-provider group model. | Sonos is the only output provider under `backend/app/services/music_sonos.py`; the UI labels the output list “Sonos” (`frontend/src/features/music/MusicPlayer.tsx:161`). | Make Sonos an adapter behind the output session model. Add adapters one at a time, using capability tokens and the same queue semantics. |
| P2 | **No explicit sleep timer or EQ surface.** Browser gain/normalization exists, but this audit found no sleep-timer or equalizer settings. | Web Audio graph exposes gain/volume (`frontend/src/features/music/musicEngine.ts:537-550`); no production sleep-timer/EQ module or UI was found. | These are inexpensive differentiators after handoff/casting. Implement locally first; do not pretend a server-side EQ applies to third-party/Jellyfin/Sonos clients. |
| P2 | **No external music scrobbling integration.** Lumina retains member playback progress and an owner-visible 90-day activity history, but it does not send plays to Last.fm, ListenBrainz, or another external scrobble service. | No production implementation was found for `scrobbl`, `last.fm`, `lastfm`, or `listenbrainz`; local progress is sent to Lumina at `frontend/src/features/music/musicSession.ts:196-203`. | If listening-history portability is requested, add an opt-in, member-owned outbound adapter with a replay-safe event cursor. Keep it separate from internal completion/progress semantics. |

## The arr question: replacement versus integration

Lumina **does not replace the arr stack today**, and ADR 0018 intentionally says it should not. It replaces the *request front end* normally supplied by Jellyseerr/Overseerr: discovery, member policy/approval/quota, deduplication/followers, request status, notifications, and post-arr scoped import. Sonarr and Radarr remain the release-management owners: lookup/add, monitored state, search, quality profiles, root folders, queue, downloads, upgrades, renaming, and file lifecycle. Lumina's native yt-dlp acquisition owns a separate problem: public online-media sources, not release-group media (ADRs 0004 and 0018).

Current integration coverage is deliberately narrow:

| System | Current Lumina role | Verified boundaries | Not currently owned by Lumina |
| --- | --- | --- | --- |
| Sonarr | Request dispatch and queue/file-status sync for shows/anime; Anime language profile bootstrap | v3 lookup, add/monitor/search, roots, profiles, custom formats, queue (`backend/app/services/requests/arr.py:52-155`) | Calendar, wanted/missing, history, manual import, release decisions, download client configuration, renaming, upgrades, tags, command UI, full library management |
| Radarr | Request dispatch and queue/file-status sync for films/anime films | v3 lookup, add/monitor/search, roots, profiles, queue (`backend/app/services/requests/arr.py:52-90`) | Same broader release-management scope |
| Lidarr | **Absent** | No `lidarr` server kind, client, routes, or schema setting found; request kinds are movie/show/anime (`backend/app/routers/requests.py:31-34`, `99-113`) | All music acquisition/monitoring/release-management integration |
| Prowlarr | **Absent** | No production client/configuration found in the audited paths | Indexer synchronization and indexer administration |
| Download clients (qBittorrent, SABnzbd, NZBGet, Transmission, etc.) | **Absent** | No production integration/configuration found | Client setup, queue/priority/control, seeding/retention, error management |

### Recommendation: integrate broadly; do not replace broadly

Keep Sonarr/Radarr/Lidarr/Prowlarr/download clients as the operational layer. A full replacement would absorb highly stateful release/indexer/client behavior while adding little to Lumina's differentiated household playback experience. The nearer-term opportunity is an **arr operations read model**, then a deliberately small set of reversible commands:

1. Extend the existing `ArrServer`/`ArrClient` seam by capability, not provider name: version, media domain, read resources, command resources, and safe configuration resources. Keep current Sonarr/Radarr request dispatch unchanged while adding Lidarr as a separate music-request flow only when music requests are a product goal.
2. Add read-only unified views for arr health, queue, history/failed items, calendar/upcoming, wanted/missing, quality profile/root mapping, and import outcomes. Lumina should correlate them to household titles and acquisition provenance without becoming a second database of record.
3. Add narrow controls that have clear ownership and idempotency: retry/search a Lumina-originated request; monitor/unmonitor a Lumina-originated item; choose an approved quality profile; cancel Lumina's pending request without deleting media. Do not expose arbitrary deletion, rename, or download-client credentials in the first pass.
4. For Prowlarr and download clients, begin read-only: health, queue states, aggregate activity/error reasons, and links back to the authoritative app. Later, permit only limited actions through the arr app that already owns the action, rather than bypassing it.
5. Reuse the existing safety pattern: admin-configured local endpoints, no redirects/proxy environment, bounded request time/bytes, content-free errors, write-only credentials, explicit path mappings, committed durable record before external dispatch, then reconciliation (`backend/app/services/requests/arr.py:1-50`, ADR 0018). Add explicit per-command audit/provenance rows before controls extend beyond a Lumina-created request.

This approach gives a household one coherent playback/request/operations experience while keeping the services that actually know releases, indexers, torrents/Usenet, and filesystem conventions authoritative.

## Architecture seams to protect

* **`playback_decision.decide` remains pure.** New device/output capabilities should become client capability inputs and session policy, not device-specific branches spread through routers (`backend/app/services/playback_decision.py`; ADR 0012).
* **The media artifact/library predicate remains authoritative for availability.** The request is available only after the scanned vault contains a visible matching title; never mark it available merely because an arr says it downloaded (ADR 0018; `backend/app/services/requests/sync.py:94-150`).
* **Keep three acquisition domains separate.** Public online acquisition is Lumina/yt-dlp; release automation is arr; browser offline copies are member-scoped music artifacts. Merging their queues or deletion policies would erase important security and provenance boundaries (ADRs 0004, 0005, 0018, 0023).
* **Use revocable capabilities for non-browser outputs.** Sonos demonstrates the correct pattern: no browser cookie on the device, a queue/item-scoped short-lived token, and revocation on logout/account changes (`backend/app/routers/music.py:289-340`, `backend/app/services/music_cast_capabilities.py:8-11`).
* **Treat generated content as untrusted.** Subtitle translation, lyrics enrichment, summaries, and any future “smart playback” model output must retain validation/provenance rules from ADR 0013.
