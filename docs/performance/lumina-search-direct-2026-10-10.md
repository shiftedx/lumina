## Changes and costs

Search now builds each explicit member-snapshot visibility expression once, projects visible title candidates in one SQL query, and reuses pure lexical field preparation. SQLite connection-local caches reuse immutable ranked refs and default Movie search cards when data and caller scope are unchanged. Limits are 128 visibility expressions, 1,024 lexical preparations, 32 ranked-ref entries and four encoded pages of at most 128 KiB each per connection. Page decoding and ordinary FastAPI serialization still run for each response. The two item-read admission slots remain unchanged.

Every request still authenticates and loads current member limits. Cache validity includes the literal caller scope, SQLite `data_version`, and the connection's `total_changes`; active transactions and pending ORM mutations bypass caching. Writes, including rolled-back writes, conservatively invalidate reuse. Model-backed/custom-encoder search, requested fields, and sorted page projections retain live rendering. This is bounded warm-query reuse, not an elimination of cold-query work. The ADR 0019 amendment documents the boundary.

The follow-up selected-version fast path loads the enabled setting, current connected-app token/member/access and visible file/root in one live SQL statement without assembling an unused title page. Primary/default selection retains the established preference path. Authentication retains inactive, orphaned, idle, revocation and touch behavior. A zero-I/O async dependency supplies the session factory; enter/query/commit/after-commit actions/close all run inside the endpoint worker before streaming. The cached SQLite shape compiler-renders 132 unique optional static policy values, including the fixed media-type lists, and leaves exactly four live request binds: token digest, cutoff and two item IDs. Member-access predicates remain live SQL expressions; this is not an authorization or result cache. Known route classification avoids needless credential parsing, exact direct-stream routes register before unrelated application routes, and Range direct streams bypass only compression's delayed identity responder.

Single ranges beginning at byte zero start with a bounded 128 KiB probe; nonzero ranges retain a 64 KiB first read and every later read uses the existing 1 MiB bulk chunk. It watches receive-side disconnects because the production Uvicorn can silently ignore sends after a player disconnects. Cancellation closes the file under a shield; concurrent response instances keep separate receivers. HEAD, invalid ranges, multipart and conditional-range parsing remain in the framework.

## Protocol

The original control uses the stopped, initialized 302-movie seed database and identical read-only media. That corpus has 302 paths but only two distinct byte streams. Four final blocks run candidate/control/control/candidate, reversing the first API/browser target between blocks. Each API scenario has ten warmups and 300 timed requests at concurrency 1, 8 and 32. Direct uses 60 fresh Chrome contexts per server per block, alternating trial order, and requires a real decoded frame. HLS uses 30 per server per block.

Direct retains prepared-source assignment-to-frame timing, which excludes authentication and MediaSources preparation. A separate sign-in-to-frame workload includes both. HLS includes PlaybackInfo and has a different timing scope. p99 is descriptive at these sample sizes; initial Chrome/GPU outliers and errors remain in raw samples.

A separate varied corpus contains 98 movies and 26 distinct byte streams: H.264/AAC at 360p–1080p, 24/25/30 fps, multiple GOP lengths, metadata sizes and faststart/end-moov MP4 layouts. Linux page-cache advice is a separate workload and does not evict the macOS host cache. Neither workload replaces the original control.

## HLS copy-seek correctness follow-up

The two host HLS failures were traced to the timestamp clock used for copied-video runs, rather than relaxed or skipped. On host FFmpeg 8.0.1, the synthetic Matroska fixture has video start time 0 and audio/container start time −0.006 seconds. The plan uses absolute video packet times, while input `-ss` normally adds the container start time. After FFmpeg's B-frame seek adjustment, this put a planned 20-second run just before its keyframe and selected the preceding one: its first video timestamp was 14.131438 seconds. Asking for absolute timestamps with `-seek_timestamp 1` produced 20.000438 seconds on the same fixture. [FFmpeg's input-seek implementation](https://github.com/FFmpeg/FFmpeg/blob/n8.0.1/fftools/ffmpeg_demux.c#L1730-L1750) shows both the container start-time addition and the B-frame adjustment.

Only planned copied-video runs now use absolute input timestamps; their output offset continues to preserve the source timeline. The original per-segment timestamp and resumed-seek assertions remain intact, and the chunk regression now covers both copied and encoded audio. Both variants failed before the fix; all 13 host seekable-HLS tests pass after it. Linux passed all 223 focused playback/HLS/client tests, including these same 13 cases; [the correctness ledger](measurements/hls-absolute-seek-2026-10-10.json) records the source hashes, image identity and test-log hashes. The Linux qualification overlay uses Jellyfin FFmpeg 8.1.2 and the same startup-warm source plus the recorded HLS command change; the earlier direct-frame measurements describe the startup-warm image, not this later correctness overlay.

The follow-up mocked-browser run also exposed an existing menu accessibility audit racing its fade-in: three focused repeats failed contrast while the settled text remained dark.
