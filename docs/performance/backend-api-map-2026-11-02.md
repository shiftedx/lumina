# Backend API performance and reliability map — 2026-11-02

## Scope and evidence

This is a read-only source audit of the FastAPI/SQLite server surface used by the
browser, iOS, tvOS, and Jellyfin-compatible connected clients. It deliberately
does not include production traffic, credentials, host names, or a production
load test. Client call graphs are documented separately in the web and native
maps; this document maps the server work those clients cause.

Evidence types are labelled throughout:

- **Measured, synthetic** is the disposable 40k-title fixture run in
  [broad observations](measurements/api-reads-2026-11-02.json) and
  [exact native observations](measurements/api-native-exact-2026-11-02.json): 20 GET samples at concurrency 1 and 6,
  lifecycle/background work off, on a contended development host. It is useful
  for relative hotspots, not a production SLO.
- **Source-observed** is a statement backed by the paths and line numbers in
  this repository as of this review.
- **Inference** is a proposed cause or remedy that needs the named validation
  before a behavior change.

The project intentionally uses a single-process SQLite design (ADR 0006), and
has substantial back-pressure already. Nothing in this audit supports a
blanket database migration or unbounded parallelism.

### Native/Jellyfin surface and aliases

The native connected-app contract is deliberately not mounted at a public
`/jellyfin/...` URL. A request for a root-compatible path such as `/Items` or
`/Users/{id}/Items` is normalized to the private internal form
`/jellyfin/items...`; literal `/jellyfin` and `/emby` client paths are retired
with 404. This preserves the SPA namespace and is security relevant
(`backend/app/routers/jellyfin.py:73-124, 998-1018`; ADR 0010).

| Native router | Templates | Method bindings | Notes |
| --- | ---: | ---: | --- |
| compatibility core | 68 | 81 | Items, resume, next-up, search, user/system and entity DTOs; two `include_in_schema=False` fallbacks at `/jellyfin` and `/jellyfin/{rest:path}` |
| direct stream router | 3 | 5 | file/rendition stream endpoints; own explicit-device-token hot path |
| music | 19 | 20 | native music views/detail |
| home | 5 | 5 | Home layout, rows and recommendation feedback |
| settings + discovery | 56 | 56 | member/server native capability and settings extensions |
| requests | 13 | 13 | connected-app request flow |
| metadata, library, streaming, watchlist, books, probes | 58 | 58 | capability-specific extensions |

Direct media paths must remain in performance/security testing even if not
OpenAPI-discovered: `/jellyfin/videos/{item_id}/stream`,
`/jellyfin/videos/{item_id}/stream.{container}`, and the M2TS IRAP index path
(`backend/app/routers/jellyfin.py:206-210`; dynamic router inventory). The
root aliases are middleware aliases, not duplicate FastAPI handlers, so route
counting them as extra endpoints would be misleading.

`/Items` and `/Users/{id}/Items` have a per-event-loop **two-slot** admission
limiter before they consume a database connection or synchronous worker
(`backend/app/routers/jellyfin.py:76-102`). This is an intentional tail
protection: it can queue a burst rather than amplify CPU/SQLite contention.

## One request: work and ownership boundaries

1. Starlette middleware enforces dynamic trusted-host, secure cookie, CORS,
   request-body boundaries and response compression; native direct-stream
   routing is added separately (`backend/app/main.py:1037-1143`). Outer
   middleware adds origin checks, failed-request logging, authenticated-activity
   accounting, security headers and bandwidth pacing
   (`backend/app/main.py:1209-1220`).
2. `get_current_user` resolves browser authentication, attaches the resource
   user, and marks eligible authenticated work active so background maintenance
   yields (`backend/app/security.py:527+`; ADR 0020). Jellyfin callers use
   token/device auth rather than browser cookies.
3. `get_db` yields one SQLAlchemy session. Request teardown commits even a
   read-only session, rolls back failures, and drains post-commit work
   (`backend/app/db.py:377-403`). That gives consistent cleanup but means a
   request-level tracing implementation should distinguish transaction teardown
   from route query time.
4. Mutations use `write_transaction`: an in-process lock, up to five seconds
   of writer admission, `BEGIN IMMEDIATE`, then post-commit work only after the
   writer is released (`backend/app/persistence.py:25-117`). A surfaced SQLite
   operational failure becomes a retryable 503 with `Retry-After: 1`
   (`backend/app/main.py:1185-1220`).
5. Ordinary JSON serialization occurs before the response reaches compression
   and, when applicable, bandwidth pacing. Do not mistake downstream pacing or
   slow-client time for SQL time.

### Database and resource policy

SQLite is opened with a five-connection `QueuePool` in this runtime and
`check_same_thread=False`, a 10-second connection timeout, WAL,
`synchronous=NORMAL`, and a 10-second busy timeout
(`backend/app/db.py:17, 317-324`). The pool observation is a local import
inspection—not a deployed capacity measurement. WAL enables concurrent readers
but SQLite still has one writer; the writer gate above is therefore a primary
reliability control.

Request body limits prevent accidental costly parsing: 2 MiB general,
15 MiB artwork, 256 MiB books, and 128 MiB photos
(`backend/app/http_boundaries.py`). Public relay/live work is capped at 24/4
and 12/2 sessions (global/per-member), with 16/4 concurrent reads and
30-second request deadlines; recording is 4/2 active jobs
(`backend/app/config.py:67-107`, wired in `backend/app/main.py:468-555`). AI
uses a maximum concurrency of three (`backend/app/config.py:157`). These are
protections to preserve, not spare capacity to consume casually.

There are also feature-local bounds: background channel/page pools (2), remote
prefetch (4 workers, 3 household/2 member), artwork fetch coalescing and slots,
book parsing, image/probe/subtitle semaphores, and controlled rendition and
reco workers. The server does not have one global thread budget. New work
should use a named, observable budget rather than silently add an executor.

## What is already efficient (preserve it)

- Browser library pages are capped at 100 (`60` default), keyset-paginated for
  recent/title views, defer `metadata_json`, request one extra row for the
  cursor, and batch owner/media-state lookup
  (`backend/app/services/library.py:159-190, 296-308, 345-374`).
- Library search has a bounded FTS result set and materializes only the requested
  page (`backend/app/services/library.py:416-443`).
- Title loading is intentionally batched; its contracts avoid one query per
  version/ancestor/progress row (`backend/app/services/titles.py`,
  `backend/tests/test_query_plans.py`).
- Jellyfin list pages hard-cap `Limit` at 1000 and use a count window when rows
  exist (`backend/app/services/jellyfin.py:67, 792-811`). This protects memory
  from arbitrary client limits even though 1000 is still expensive.
- The native response limiter, socket caps (256 total / 4 per token) and
  bounded socket size/lifetime protect connected clients
  (`backend/app/routers/jellyfin.py:86-102, 959-995`).
- Background maintenance is activity/quiet-window aware (ADR 0020), and
  household resource budgets are explicit (ADR 0024).

Existing regression coverage worth retaining when changing these areas:
`test_library_pagination.py`, `test_query_plans.py`,
`test_jellyfin_performance.py`, `test_jellyfin_query_budget.py`,
`test_jellyfin_search_cache.py`, `test_navigation.py`,
`test_requests_catalog.py`, `test_persistence_transactions.py`,
`test_sqlite_watch_write_serialization.py`, `test_http_boundaries.py`,
`test_bandwidth.py`, and `test_origin_middleware.py`.

**Focused-contract qualification:** the review's focused run of
`test_jellyfin_performance.py`, `test_jellyfin_query_budget.py`, and
`test_persistence_transactions.py` produced 33 passes and one fixture failure.
`test_jellyfin_title_batch_skips_unused_artwork_loading` supplies a fake mapper
with `db=None`, but a newer collection-art fallback now calls `db.scalars` in
`backend/app/services/jellyfin.py:611`. That is a stale unit-test double, not
evidence of a production request exception. Preserve the collection fallback;
repair the fake or test its observable DB-backed behavior before using this
focused group as a green gate.

## Measurements and source explanation

| Endpoint/shape | Synthetic measurement | Source interpretation |
| --- | --- | --- |
| browser `GET /api/library`, 50 rows | 6 SQL, 39.7 KB, median 89.6 ms at C1 / 733.7 ms at C6 | bounded set-based hydration; the count does **not** indicate N+1 |
| native `/Items`, exact Lumina catalog fields/sort, 50 | 6 SQL, 22.3 KB, 16.6 / 62.2 ms | projected catalog is comparatively cheap |
| native `/Items`, broad default DTO, 500 | 6 SQL, 465 KB, 116 / 795 ms | payload/DTO materialization dominates more than query count; this is not the normal catalog projection |
| native `/Items`, exact recent DateCreated fields, 50 | 7 SQL, 54.6 KB, 200.7 / 1734.2 ms | investigate statement/order/index and count window before changing the native UI |
| native Home rows | 72 SQL, 130 KB, 273.9 / 780.9 ms | multiplexer executes many shelf builders and mapper batches in one request |
| `GET /api/navigation` | 11 SQL, 93 B, 11.7 / 34.2 ms | tiny response currently pays content-availability and policy probes |

The browser library page query was also compiled and explained against the
same synthetic fixture for an admin, with no mutation. SQLite used
`MULTI-INDEX OR` on the shared/user visibility alternatives and then `USE TEMP
B-TREE FOR ORDER BY` for `(downloaded_at DESC, created_at DESC, id DESC)`.
This is concrete evidence of planner/sort work behind a six-query request, but
only for that user shape. It is not proof that every role or real library has
the same plan. The visibility predicate documents this trade-off and avoids a
known worse scan in non-driving queries (`backend/app/services/library.py:823-841`).

## Ranked opportunities

### P1 — reduce Native Home’s shelf fan-out before adding caching

**Source-observed:** `GET /jellyfin/lumina/home/rows` can construct fourteen
allowlisted shelf types, each capped at 20, plus up to four smart collections;
the configured layout invokes builders serially then performs an additional
title/ancestor metadata hydration pass (`backend/app/routers/jellyfin_home.py:35-40,
123-130, 133-228, 271-345, 381-421`). It may also merge cached external
snapshots when explicitly requested and enabled. The 72-query synthetic result
is consistent with this composition, not with one accidental row-by-row ORM
lookup.

**Recommendation:** profile SQL/query time by shelf and DTO helper for the
actual native layout, then form a request-scoped plan: collect title/item IDs
across shelves, reuse one title batch/metadata map, and share repeat lookups
(notably watchlist/progress). Keep shelf ordering, per-member visibility,
external gating, 20-item caps and partial-empty-row behavior unchanged. Smart
collection evaluation should remain separately budgeted; it is not safe to
blindly parallelize all shelf builders on SQLite.

**Acceptance evidence:** exact native Home benchmark at C1/C6, per-shelf SQL
breakdown, no change to `test_jellyfin_query_budget.py`/visibility contracts,
and a response-equivalence fixture for a mixed movie/episode/watchlist layout.

### P1 — cache/persist the *coarse*, anime-only language availability

**Source-observed:** the request catalog title route defaults
`include_languages=true` (`backend/app/routers/requests_catalog.py:64-70`).
Availability builds a visible-artifact query, loads and parses up to 501 rows
and sidecar/probe facts, and performs a separate derived COUNT
(`backend/app/services/requests/languages.py:33-85`). This is exactly the
wrong place to compute per-episode detail when the product decision is only
“does this anime have English audio, and/or English subtitles?”

**Recommendation:** maintain an invalidatable title-level availability summary
at import/probe/scan time for anime classification only: `has_non_english_primary`,
`has_english_audio`, `has_english_subtitles`, with a scan/version timestamp.
Return it from catalog annotation; request a detailed episode matrix only from
an explicit diagnostic/manage action. Backfill lazily with a short stale marker
if old titles lack the summary. Do **not** apply this product behavior to movie
or show requests.

**Acceptance evidence:** cold and warm request-detail traces; a title with
mixed versions; rescans/artifact removal invalidating the summary; no per-file
tracks in normal response; preserve `test_requests_catalog.py` behavior where
detail is intentionally requested.

### P1 — make navigation availability cheap without making it stale forever

**Source-observed:** every `/api/navigation` response uses `Cache-Control:
no-store` and runs three indexed title-wall probes plus music, saved-video,
recording, book, and photo existence probes, settings/access, and request
policy checks (`backend/app/routers/navigation.py:11-13`,
`backend/app/services/navigation.py:27-78`). The synthetic 11-SQL/93-byte
result is direct evidence.

**Recommendation:** cache this member-scoped capability document for a very
short TTL or against explicit generation counters for library/access/settings
changes. Invalidate on import/delete/visibility change, member access change,
settings/request-policy change, and source enablement change. Use the current
uncached path for invalidation failures; do not turn it into a cross-user cache
or hide a just-revoked feature.

### P2 — give catalog provider work shared admission and single-flight

**Source-observed:** request-catalog TTL cache entries are in-process and
unsynchronized, so simultaneous cache misses may fetch the same remote data;
each catalog call creates a new `ThreadPoolExecutor(max_workers=8)`, and Home
can build nine rails (`backend/app/services/requests/catalog.py:62-83, 480-508`).
Routes are synchronous because provider calls are blocking.

**Recommendation:** a keyed single-flight layer with stale-while-revalidate
and a service-lifetime, instrumented bounded provider executor. Bound waits and
return a cached/stale known-safe result where the current product contract
allows it. Do not hold a SQLite writer or request transaction while waiting on
provider I/O. Preserve the existing provider rate limits/timeouts and request
cache TTL semantics.

### P2 — improve library page plan only after role-specific plans prove it

**Measured + source-observed:** six SQL statements, not N+1, explain browser
library hydration; the fixture plan has OR-driven index work and a temp sort.
At C6 the measured median rises sharply. A narrower, ordered query for the
admin/ownerless/shared union, a materialized visibility key, or a compatible
covering index might help, but each affects member visibility semantics and
write/index cost.

**Recommendation:** capture `EXPLAIN QUERY PLAN` and SQL timing for admin,
ordinary member, restricted member, first page and cursor page at realistic
media proportions. Choose a single plan/index change only if it improves both
the normal read and an accepted write budget. Continue using keyset pagination
and deferred metadata. Do not use an offset workaround or a generic cache that
leaks visibility.

### P2 — measure continuation usefulness before changing page size

**Measured:** the actual field-projected catalog 50 is 22.3 KB / 16.6 ms C1;
its 500-item continuation is 219.8 KB / 40.9 ms C1 and 282.0 ms C6. The
broad default DTO 500 is a distinct 465 KB / 116 ms C1 probe, not the current
native wall query. The server's 1000 cap is a guardrail, not a target
(`backend/app/services/jellyfin.py:67, 473-475`).

**Recommendation:** preserve the existing first-50 publication and light
projection. Measure whether remaining serial catalog pages are used before
navigation/query changes, and compare demand-aware/suspendable continuation.
Do not blindly shrink every 500-item continuation to 50–100: that multiplies
round trips when a complete local catalog is actually required. Retain
server-side bounds and third-party protocol compatibility. See the native map
for the filtering/alphabet-jump correctness constraints.

**Acceptance evidence:** first usable page, total/paged completion requests and
bytes, abandoned work, filter/alphabet/scroll semantics and member/query
isolation on fast and shaped networks.

### P2 — expose contention rather than guessing at it

**Source-observed:** the server already records writer admission/busy/wait
metrics (`backend/app/persistence.py:42-68`), but route decisions need a
correlated view of endpoint duration, SQL count/duration, pool checkout wait,
Jellyfin limiter queue wait, response bytes, remote-provider wait and executor
queue depth. Background loops and several local executors make host-level CPU
alone insufficient to diagnose a spike.

**Recommendation:** add low-cardinality route-template telemetry with sampled
slow-query plans/parameter-free fingerprints, plus dashboard panels for the
existing writer/resource gates. Never record tokens, raw URLs, query terms,
paths, or provider headers. Use this before changing middleware such as
compression/bandwidth pacing, which serves a broader resource policy.

### P3 — audit scheduler overlap and per-call executor creation

**Source-observed:** maintenance/automation loops deliberately yield to active
members, but some services create short-lived pools (catalog, source refresh,
some discovery paths) while others own long-lived pools
(`backend/app/main.py:700-925`; `backend/app/services/requests/catalog.py:81-83`).

**Recommendation:** inventory each executor/slot at startup and export active,
queued, rejected and wait-time counters. Consolidate only pools with the same
blocking resource and cancellation semantics—combining ffmpeg, provider I/O
and SQLite work into one generic pool would reduce reliability.

## Focused validation to run with an implementation

1. Re-run the synthetic scripts with lifecycle on and off, C1/C6, and capture
   median plus p95/response bytes/SQL counts. Compare the exact native field
   projection, not only a broad default DTO.
2. Add a deterministic fixture for an anime title with Japanese primary audio,
   mixed English dub availability, and missing English subtitles; assert the
   normal request card reads only its persisted summary.
3. Run the focused existing contracts named above, particularly pagination,
   native query budget, navigation visibility, request catalog, writer
   serialization and HTTP boundary tests. A full release gate remains the
   integration owner’s responsibility.
4. Test active playback/relay/recording with a concurrent Home, library and
   navigation burst. Success is bounded queueing/503 retry behavior rather
   than unlimited concurrency.
