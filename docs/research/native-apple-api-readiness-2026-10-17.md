# Native iOS + tvOS API readiness — 2026-10-17

## Decision in brief

Lumina can support a narrowly scoped native iOS/tvOS **video proof of concept now through its opt-in Jellyfin-compatible API**, rather than by teaching AVPlayer to consume the cookie-authenticated `/api` player endpoints. That surface already supplies non-browser device credentials, a server identity, catalog/detail/search, member-scoped progress and favorites, direct byte-range playback, and HLS conversion. It also deliberately puts `ApiKey` on every HLS child URL because AVPlayer cannot be assumed to retain request-header authentication while it loads a playlist's segments and initialization map.

That is spike acceleration, not the launch architecture. Everyday viewing includes Lumina-specific Home/recommendations, member profile/preferences and AI-discovery behavior that the Jellyfin facade does not promise as a first-party UX. The launch therefore needs a **curated first-party native boundary** over existing Lumina services, plus a native Connected-App credential flow. The native `/api` surface is currently broad but browser-shaped: its normal credential is an HttpOnly cookie plus CSRF on writes; its HLS session URLs require that credential on every request. Its agent bearer is an administratively created Connected App token, not a native pairing/refresh protocol. Do **not** make a native app depend on that cookie route or invent a second, unaudited token system.

The recommended sequence is:

1. Ship a device-local iOS/tvOS POC against the Jellyfin facade with one manually entered server address, username/password sign-in, a stable client-generated `DeviceId`, and Keychain storage of its device token. Keep the facade opt-in.
2. Qualify direct playback and the existing HLS fallback on actual iPhone/iPad/Apple TV hardware. Send Jellyfin `DeviceProfile` data; use the returned direct URL or returned HLS URL verbatim. Report progress through the existing Jellyfin session endpoints.
3. Add the narrow first-party native boundary for Lumina Home/recommendations, profile/preferences, search/detail, progress/favorites and AI-discovery. Reuse the existing `device_tokens`, member-visibility predicate, playback decision and progress services; do not clone the whole browser API.

This is a source audit, not a runtime/device qualification. It was performed against the working tree at `a4e01da` plus uncommitted changes present on 2026-10-17. The uncommitted music-session and track-preference work is called out below rather than represented as committed-release behavior.

## Premium playback: current reality and required launch work

The current decision engine is a good base, but it is not an Infuse-quality promise yet. It takes a client-declared container/codec/range/channel profile, preserves the least-work path (`direct > remux > audio encode > video encode`), recognizes HDR10/HLG/Dolby-Vision-derived ranges, and copies H.264/HEVC/AV1/VP9 video plus AAC/AC-3/E-AC-3/FLAC/Opus audio into its HLS path when the client profile permits it ([`playback_decision.py:1-23`](../../backend/app/services/playback_decision.py#L1-L23), [`playback_decision.py:122-197`](../../backend/app/services/playback_decision.py#L122-L197)). Thus a correctly profiled, compatible direct-play or remux path can preserve source HDR/Dolby Vision and supported audio rather than needlessly convert it.

The limits matter:

- HDR is currently tone-mapped to SDR whenever video must be encoded; H.264 output tops out at 1080p. Dolby Vision profile 5 is unavailable if the server lacks its OpenCL reshape route ([`playback_decision.py:177-195`](../../backend/app/services/playback_decision.py#L177-L195); ADR 0012). An image subtitle the client cannot render forces video encode/burn-in, so it also loses HDR and can turn an otherwise direct/remux source into SDR ([`playback_decision.py:149-152`](../../backend/app/services/playback_decision.py#L149-L152), [`local_playback_sessions.py:179-185`](../../backend/app/services/local_playback_sessions.py#L179-L185)). Text/WebVTT sidecars do not have that cost.
- HLS audio copying includes AC-3 and E-AC-3, while an unsupported codec/channel layout encodes to AAC at up to six channels ([`playback_decision.py:20-23`](../../backend/app/services/playback_decision.py#L20-L23), [`local_playback_sessions.py:225-231`](../../backend/app/services/local_playback_sessions.py#L225-L231)). The code does not establish AVPlayer support for arbitrary TrueHD/DTS lossless passthrough or arbitrary Blu-ray Dolby Vision profile/container combinations. A device profile must only advertise formats proven on that device and output chain.
- The conversion master contains one variant, so local media has manual quality/restart behavior, not adaptive-bitrate HLS ([`local_playback_sessions.py:335-339`](../../backend/app/services/local_playback_sessions.py#L335-L339)). This is the material gap for robust away-from-Wi-Fi viewing. Remote provider playback may retain upstream ladders, but it does not solve local-library ABR.

"Parity with Infuse" should therefore mean parity for the selected network-media classes: direct/remux preservation of supported HDR10/Dolby Vision and E-AC-3/Atmos where the real Apple device and output chain prove it, text subtitles without conversion, image-subtitle fallback, and a safe H.264/AAC SDR fallback. It cannot honestly mean universal local-file/container, Blu-ray Profile 7, TrueHD/DTS lossless passthrough, or ISO parity solely because AVPlayer is used. Those are separate source-container, codec/profile, and physical-output-chain qualifications.

Required shared-server work for the selected launch scope is **3.5–6.5 person-weeks** beyond the first-party native API boundary: (1) an Apple device-profile fixture/matrix and PlaybackInfo contract qualification; (2) HDR/Dolby-Vision direct/remux and HLS metadata/manifest correctness tests; (3) explicit audio capability/fallback handling for AAC, AC-3 and E-AC-3/Atmos; (4) subtitle-selection policy that prefers sidecar text and presents the HDR-costly image-subtitle fallback honestly; and (5) a bounded two/three-rung local HLS ABR ladder for constrained remote networks. It excludes native player-engine UI, Apple hardware procurement and real-device QA time.

## Apple platform implications

Apple documents AVFoundation as supporting HLS playback, and its HLS authoring specification lists H.264, HEVC, Dolby Vision and AV1, fMP4 for HEVC, WebVTT, correct HLS MIME types, TLS, and per-device/changing segment URLs as compatibility/security guidance ([AVFoundation](https://developer.apple.com/av-foundation/), [Apple HLS authoring specification](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html)). Lumina's HLS output is fMP4 (`init.mp4` plus `.m4s`) and returns `application/vnd.apple.mpegurl` for manifests ([`local_playback.py:245-260`](../../backend/app/routers/local_playback.py#L245-L260)); its H.264/H.265 paths and software/hardware conversion are therefore directionally aligned, but actual codec/profile/HDR/pass-through compatibility must be discovered by a native `DeviceProfile` and hardware testing.

The same Apple specification advises changing media-segment URLs per device/time and requires modern TLS for protected delivery. Lumina's existing Jellyfin token-in-URL propagation is the practical choice for AVPlayer subrequests, but it is a **long-lived device credential**, not a short-lived media capability. Existing revocation and per-request visibility checks reduce the exposure, yet query values can enter access logs. Retain ADR 0010's proxy-log redaction requirement; a first-party native API should eventually return short-lived, item/session-bound playback capabilities in every manifest and stream URL.

HDR, Dolby Vision, Atmos/passthrough, and AV1 should not be promised by server capability alone. Apple's HLS guidance allows formats subject to codec/profile/device limits, describes Dolby Vision profile requirements and E-AC-3 JOC signaling, and Apple's own sample guidance says AV1 playback requires hardware support ([Apple HLS authoring specification](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html), [Apple HLS examples](https://developer.apple.com/streaming/examples/)). Lumina currently offers a safe H.264/AAC conversion fallback (ADR 0012); preserve that as the baseline on iOS and tvOS.

## Recommended native authentication and playback shape

For the POC, use the existing Jellyfin contract end to end:

1. The user supplies a canonical Lumina public or configured LAN address. Probe `/System/Info/Public`; require the household to have opted into Jellyfin in settings.
2. Call `/Users/AuthenticateByName` with a stable random `DeviceId`, product/client/version. Store the returned access token in Keychain, never in `UserDefaults`. Sign-out calls `/Sessions/Logout`, which revokes that device Connected App.
3. Browse through `/UserViews`, `/Items`, title/item routes, and search. Keep Lumina/Jellyfin IDs opaque.
4. Request `/Items/{id}/PlaybackInfo` with a truthful Apple `DeviceProfile`, desired audio/subtitle stream indexes, position and `PlaySessionId`. Direct play uses the supplied stream URL with `ApiKey`; fallback uses the returned HLS playlist URL. Let the server's pure decision choose direct/remux/transcode.
5. Send `/Sessions/Playing`, `/Sessions/Playing/Progress`, and `/Sessions/Playing/Stopped`; use the returned/user-data state for resume, favorites and played state. Fetch external subtitle URLs exactly as returned.

For the launch native boundary, issue a first-class `kind=native` Connected App token with device-bound naming, secure browser/device-code approval, one-time pairing result, rotation and explicit scope. Return short-lived opaque playback capabilities (bound to member, device token, item/version, permitted rendition and expiry) and rewrite every HLS child URL with that capability. Keep device refresh identity separate from the stream capability. Reuse `DeviceToken`, `jellyfin_stream_user`'s live validation pattern, `LibraryService.visible_predicate`, `PlaybackProgressService`, and the existing `decide()`/session machinery; do not duplicate permission or transcoding code.

## API compatibility and conditional code generation

Lumina disables `/openapi.json`, Swagger and ReDoc by default (`LUMINA_ENABLE_API_DOCS`, [`main.py:1000-1007`](../../backend/app/main.py#L1000-L1007)). Even when enabled, FastAPI's generated schema reflects all internal browser/admin routes and is not a release-versioned native contract. Some endpoints return raw `dict`, dynamically shaped Jellyfin DTOs, or feature-conditional payloads; the facade intentionally also normalizes some errors to empty bodies for client compatibility ([`main.py:1085-1095`](../../backend/app/main.py#L1085-L1095)). Generating Swift clients from the current entire schema would create a fragile, over-broad SDK and can accidentally expose admin/browser surfaces as supported.

Launch needs a curated versioned native contract and compatibility fixture, with explicit stable models, nullable fields, opaque ID/string rules, cursor/error/retry semantics and media URL lifetime. It does **not** need to expose the whole app schema or commit to generated Swift code. If the client team elects code generation, publish a separate curated OpenAPI document, pin the generator and run a generated Swift package compile/test in the release gate. Treat Jellyfin as a separately versioned compatibility adapter, not the source for Lumina-native code generation.

## Readiness acceptance checklist

- [ ] Remote HTTPS or explicit LAN-HTTP deployment satisfies ADR 0001; test address is canonical and proxy access logging redacts query strings.
- [ ] Jellyfin integration is explicitly enabled; `/System/Info/Public` and `/Users/AuthenticateByName` work with the target app's stable `DeviceId`.
- [ ] Sign-in token is Keychain-stored; logout/revocation immediately prevents catalog, direct range and HLS segment access.
- [ ] A visibility-restricted member cannot discover, play, subtitle-fetch, favorite or resume an excluded item through the native path.
- [ ] On representative iOS and tvOS hardware: H.264/AAC direct Range playback, a forced HLS conversion, seek, pause/resume, external WebVTT and alternate audio all work.
- [ ] Playback progress, completed state, favorite and continue-watching agree between web, native client and an existing Jellyfin client.
- [ ] Device-profile test covers at least one incompatible source and proves server fallback to H.264/AAC HLS; HDR/Atmos/AV1 only ship after their own device matrix passes.
- [ ] POC does not rely on `/api` session cookies, agent-token provisioning, browser offline caches or the uncommitted music-session route.
- [ ] The narrow native boundary has a versioned compatibility fixture before app code treats it as stable; a generated Swift smoke test is added only if the team selects code generation.

## Relevant architecture decisions

- ADR 0001 defines the loopback/HTTPS-proxy/LAN deployment boundary.
- ADR 0010 makes Connected Apps the non-browser credential and Jellyfin an opt-in, root-mounted compatibility API.
- ADR 0012 centralizes playback decisions and uses an H.264/AAC-compatible conversion path.
- ADR 0013 requires AI output validation and non-AI fallback behavior.
- ADR 0019 puts member visibility inside the shared predicate.
- ADR 0022 separates books and their format-aware reading state from media playback.
- ADR 0023 confines offline music to owner-scoped browser storage and grants Sonos capability URLs instead of browser credentials.
- ADR 0026 (currently uncommitted in this worktree) supplies revisioned member music sessions, but does not define a native auth contract.
