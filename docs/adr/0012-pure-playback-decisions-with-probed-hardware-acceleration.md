# ADR 0012: Pure playback decisions with probed hardware acceleration

- Status: Accepted
- Date: 2026-09-25

## Context

The web player and Jellyfin clients need direct play when possible, and a hardware transcode otherwise, including 4K HDR tone-mapped to SDR on common Intel, AMD and NVIDIA Linux servers. Jellyfin 10.11 transcoded everything by treating unknown device-profile conditions as failures. The previous container dropped supplementary groups (`gosu`), so `/dev/dri` was unreachable. Re-encoding audio only to normalize loudness or mute words wastes CPU and breaks direct play.

## Decision

- The playback decision is one pure, table-tested function, `decide(client caps, streams, limits, audio, subtitle)`. Its preference order is direct > remux > audio-only encode > video encode. Video is never re-encoded because of audio or a text subtitle. Unknown profile conditions are ignored, and reasons use Jellyfin's `TranscodeReasons` names. Those reasons travel in the `TranscodingUrl` query string (`TranscodeReasons=...`), the field Jellyfin clients read them from; `MediaSourceInfo` JSON never carries them.
- A client audio bit-depth ceiling is checked against normalized probe facts for direct delivery and HLS stream copy. Unknown depth or an exceeded ceiling keeps audio conversion while compatible video stays copied. The native FLAC profile uses this to retain 16/24-bit lossless audio without falsely advertising 32-bit decoding.
- Hardware acceleration (`auto|off|qsv|vaapi|nvenc|rkmpp`) is probed at startup with a one-frame H.264 encode, then independently probes HEVC and AV1 where the selected backend declares them. Linux `auto` tries Intel QSV, NVIDIA NVENC, VA-API, then Rockchip MPP; a supported Rockchip BSP host should select RKMPP explicitly to skip unrelated probes. QSV and VA-API use the configured DRM render node, NVENC/NVDEC/CUDA use the configured visible CUDA GPU, and RKMPP uses a probe-gated CPU-frame upload to its MPP device. An eligible Rockchip SDR 8-bit 4:2:0 session without tone mapping or burned subtitles can additionally pass a per input/output-pair probe: synthetic H.264, HEVC, VP9, or AV1 input must pass its exact RKMPP DRM-PRIME decoder, a non-trivial RGA scale, and the requested H.264/HEVC MPP encoder, then produce a readable media frame. The result is not generalized across codecs, and a failed pair stays on the CPU-upload path. Hardware decode is used only when that input is accepted; a session may retain hardware encode after falling back to software decode. A hardware session that fails before its first manifest retries once in software, and repeated hardware failures pin the process to software until restart.
- The container ships jellyfin-ffmpeg, Mesa VA-API userspace drivers and the Intel OpenCL runtime on amd64. The NVIDIA driver is host-owned and mounted by NVIDIA Container Toolkit; the image never bundles a proprietary NVIDIA library. The arm64 jellyfin-ffmpeg package also ships Rockchip MPP/RGA userspace libraries, but those require an arm64 Rockchip BSP kernel and host-owned device permissions. The `setpriv` drop grants only explicit host render/video groups. Separate Compose overrides pass DRM, NVIDIA, or the four known Rockchip VPU paths; the Rockchip override retains the base AppArmor/system-path policy and never enables privileged mode. The probe keeps a misconfigured host on software conversion.
- HDR preservation is frozen in `Decision.video_range`, independently of source/direct-play ranges, and travels through resource preview/admission and pending Jellyfin playback. Client `transcode_ranges` and server `encode_ranges` must match exact HDR10 or HLG with 10-bit BT.2020 limited-range source facts. A separate demand-driven encoder proof validates codec, every HLS fragment, nonzero seek, CICP, full mastering-display metadata and content-light levels within an eight-second total codec/range budget; it uses a local HEVC `libx265` fixture, independently of whether AV1/VP9 source synthesis is available. Hardware decode is an additional cached exact `source codec + known 10-bit 4:2:0 pixel format -> output codec/range/backend/verifier/device` proof. QSV, VA-API and NVDEC use device-native P010 filtering; VideoToolbox has an explicit hardware-decode → P010-download → CPU-scale → hardware-encode boundary and makes no zero-copy claim. A decoder failure revokes only that exact pair and falls back to CPU decode/P010 upload with the already-proven selected encoder; only a later hardware-session failure retries the independently proven software encoder. AMF and RKMPP do not qualify HDR hardware decode. Missing verifiers, failed encoder proofs, Dolby Vision, HDR10+, tone mapping, or image subtitle burn-in cannot advertise an HDR encode. Explicit diagnostics clears cached decoder observations and requalifies encoder ranges/Rockchip pairs without running decoder-pair probes; read-only diagnostics reports cache state without starting HDR/pair probes.
- A passing OpenCL or CUDA tone-map path enables Dolby Vision profile 5 reshaping. CUDA uses the metadata-preserving NVDEC path and explicit DOVI processing; a failed DV5 session is never sent through the software tone mapper. The synthetic PQ probe checks the pipeline, while RPU metadata handling still requires a real DV5 sample on the target GPU.
- Native servers also accept `videotoolbox` (macOS) and `amf` (Windows) when their FFmpeg and drivers pass the encoder probe. macOS auto selects VideoToolbox; Windows tries QSV, NVENC and AMF. A passing VideoToolbox HDR decoder pair still downloads P010 into the shared CPU scale before hardware encoding; AMF uses CPU decoding and filtering. The Windows server path remains unqualified. These native backends are not available inside the Linux image.
- Loudness normalization and profanity mute are applied in the browser by one shared Web Audio graph. Audio is never re-encoded for either, and ffmpeg `volume=` is added only when audio is already being encoded for a Jellyfin client.

## Consequences

- Linux Docker Engine supports Intel QSV, Intel/AMD VA-API and NVIDIA NVENC/NVDEC/CUDA when the host driver, container access and its installed GPU capabilities permit them. Docker Desktop for Mac has no `/dev/dri` and NVIDIA Container Toolkit does not support it, so the Linux image remains software-only there. Native VideoToolbox and AMF are outside this Linux container deployment.
- One encode per session bounds GPU cost. Quality changes restart the session at the current position.
- H.264/AAC remains the compatibility output. HEVC or AV1 HLS video is chosen only when the client explicitly advertises it and the selected backend passed that codec's actual probe; software retry independently proves the modern encoder before use. Modern output is SDR 8-bit by default, or 10-bit HDR10/HLG after an exact client/server range match, up to 2160p within client/member/bandwidth limits. Dolby Vision/HDR10+ preservation while encoding remains unsupported. Rockchip only advertises H.264/HEVC from its RKMPP probe. Its zero-copy path is limited to individually qualified SDR source/output pairs; AV1 encoding, HDR-preserving output, subtitle zero-copy, and OpenCL HDR tone-mapping remain unsupported.
- Mute and normalization are web-player features. Infuse and other apps play unfiltered, and the settings copy says so.

## Roku audio rendition compatibility

Roku HLS playback exposes separate fMP4 video and audio renditions because some Roku decoders play combined fMP4 video without audio. The existing decision and encoder stay shared; completed segments are remuxed once into cached video-only and audio-only segments without re-encoding. Both playlists use the same whole-file plan and packet timestamps. Cached renditions count against the existing playback cache cap and disappear with the session. Other clients retain combined fMP4 delivery.

Roku's HLS fallback uses stereo AAC even when its profile advertises Dolby passthrough. Copied EAC3 can leave an unreadable fMP4 initialization header, and the separate Dolby rendition can fail in the player. Compatible direct playback retains the client's original audio capabilities; the fallback still copies video whenever possible. PlaybackInfo and the session use the same fallback capabilities.
